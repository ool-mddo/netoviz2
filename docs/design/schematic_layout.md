# schematic レイアウトの設計

schematic は、netoviz2 の 3 つ目のレイアウトエンジン (`?layout=schematic`) で、**実務のネットワーク構成図に近い配置**を作ります。
向き・並び・位置に意味を持たせます (上流が上、拠点が左右、冗長ペアが横並び)。全体の構成は [../architecture.md](../architecture.md)、
プロファイルの書式は [profile_format.md](profile_format.md)、他のエンジンとの比較は [layout.md](layout.md)、計画と判断の経緯は [../work/plans/schematic_layout.md](../work/plans/schematic_layout.md) を参照してください。

## 1. 考え方

### なぜ別のエンジンが要るか

stress や force は、「グラフ上の距離を画面上の距離に写す」手法で、向きに意味がありません (回転・鏡映しても同じ評価)。構成図では、**向きそのものが情報**です。
上流が上、西が左、主系が左、東京と大阪で同じ役割が同じ高さ、といった「設計の意図」は、接続の関係からは導けません。目的関数の時点で食い違います。

| 観点          | stress / force                                    | 構成図に必要なもの                                        |
| ------------- | ------------------------------------------------- | --------------------------------------------------------- |
| 向き          | なし (配置のたびに変わる)                         | 上流が上、拠点が左右、主系が左、という意味づけられた向き  |
| 整列          | なし                                              | 拠点をまたいだ行の整列 (拠点が違っても同じ役割は同じ高さ) |
| 冗長ペア      | 偶然にしか並ばない                                | 隣り合って、左右の順序が決まっている                      |
| 安定性        | 開き直すたびに変わる                              | 論理図と物理図、版の前後で、位置関係が保たれる            |
| L3 セグメント | 点として扱う (多数の機器をつなぐと密なハブになる) | 機器の間に収まる接続点                                    |

### 設計原則 (作図の考え方)

実務の構成図の作図の考え方を、エンジンが扱うことにまとめたものです。「位置は最も強い視覚変数であり、設計上の意味を割り当てる」が根本にあります。

| #   | 原則                                                                | エンジンでの扱い                                                             |
| --- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| P1  | 縦軸は上流 (外部) から下流 (端末)。セキュリティ水準もこの向きに並ぶ | ノードに階層 (tier) を与え、行を単調に割り当てる                             |
| P2  | 横軸は地理 (西→東)、主系→副系                                       | グループ (拠点) に順序 (order) を与え、左右の順序を固定する                  |
| P3  | 同じ役割は同じ高さに並べる                                          | 同じ tier のノードは同じ y                                                   |
| P4  | 冗長ペアは水平に並べ、同じ形・左右対称にする                        | ペアは 1 つの単位として隣り合わせ、主 (番号が小さい) を左に置く              |
| P5  | 近接はまとまり。グループ内は詰め、グループ間は開ける                | グループ間の間隔を広くとる                                                   |
| P6  | 同じものは同じ形で描き、差分を目立たせる                            | (未対応: 同型のグループで配置を共有する。ステージ 2b)                        |
| P7  | 他の図と位置関係をそろえる (論理図と物理図)                         | 下位レイヤの配置を support をたどって引き継ぐ                                |
| P8  | 線は直線が基本。ノードに重なるときだけ折れ線にし、角を丸める        | 直線で済むリンクは直線のまま。重なるものだけ、水平・垂直の折れ線             |
| P9  | ペアの線は平行・等間隔                                              | (一部: 同じノードから同じ側に出る線の脚を、互いにずらす)                     |
| P10 | L3 セグメントは横線 (バス)、接続ノードは縦線でぶら下げる            | 試したが見送った (「7. 見送ったもの」)                                       |
| P11 | 物理・論理の合成図は、機器の箱に入れ子で描く                        | 対象外                                                                       |
| P12 | パターンがあるから省略できる。例外は目立たせる                      | 例外 (階層が付かない、相手のいないペア) を報告する。折り畳みは未対応         |
| P13 | 目的で載せる要素と粒度が変わる                                      | 物理 / 論理のビューをプロファイルで切り替える (ビューごとに別のプロファイル) |

### 対象

トポロジの**1 レイヤずつ**の物理図・論理図を描きます。全体概要図 (データが無い) と、複数レイヤを束ねる合成図は、対象外です。

## 2. 全体の構造

3 つを分けて持ちます。

- **ダイアグラムプロファイル:** どのノードがどの拠点・階層・ペアに属するかを、CSS のようにセレクタで宣言する、トポロジとは別の YAML ([profile_format.md](profile_format.md))。ドメインの知識は、すべてここに置く。コードは、`kind`・ユースケース・ネットワーク名・命名規則で分岐しない。
- **推論と継承:** プロファイルが無くても、下位レイヤの配置の引き継ぎや、名前とリンクからの推論で、拠点・階層・ペアを決める。
- **ソルバと経路:** 離散的な配置 (グループ・行・並び) と、座標の決定、リンクの経路。

レイヤごとに、意味を付ける方法を次の順に試し、最初に合うものを使います。

1. そのレイヤの**プロファイル** (`target.layer` が一致するもの。`inherit` を書いたときは、そのレイヤからの継承)
2. **下位レイヤからの継承** (support をたどる)
3. **名前とリンクからの推論**
4. stress (フォールバック)

## 3. 配置の流れ

```
annotate (意味付け) → slots (離散的な配置) → solve (座標) → connectors (接続点) → 位置
                                                                    ↓ (描画時)
                                                            linkRouter (リンクの経路)
```

### annotate: 意味付け (`annotate.ts`)

ノードの名前 (ID ではなく `name`) をプロファイルの正規表現で分解し、規則を**後に書いたものが勝つ**順に適用して、各ノードに階層 (tier)・拠点 (group)・順序 (order)・冗長ペア (pair) を付ける。
どの規則からも階層が付かないノードは、「分類できない」例外として報告する。

### slots: 離散的な配置 (`slots.ts`)

- 拠点 (group) を `order` で左右に並べる (順序の無い拠点は名前順。拠点の無いノードは最後)。
- 階層 (tier) を行にする。**行は拠点をまたいで共有**する (どの拠点でも同じ役割が同じ高さ)。
- 冗長ペアは、同じ拠点・同じ行の 1 つの単位として動かす (主が左)。
- 行の中の順序は、重心法 (隣の行のノードの位置の平均で並べ替える) で交差を減らす。下位レイヤの位置が与えられたときは、その順序を保つ。

### solve: 座標 (`solve.ts`)

- y: 行ごとに同じ。行の間隔は、ノードの半径と行間隔の定数で決まる。 円どうしの間隔の既定値は、行間 120、同じ拠点のノード間 60、ペア間 60、拠点間 160 (px。ラベルを置く余裕のため)。継承するレイヤの機器間は 100 (`index.ts` の `DEVICE_GAP`)。
- x: 行ごとに、順序を保ったまま最小間隔を確保する最小二乗 (`bands.ts` の `spaceOutWith`。PAV 法)。ノードの希望位置は、他の行のつながり先の位置の平均 (リンクが縦に近づく)。ペアは、2 つの希望位置の中心に置く。
- 拠点は、全行を通じて 1 つのブロックとして扱い、拠点どうしが重ならない。

## 4. 推論 (`nameShape.ts`、`infer.ts`)

プロファイルが無いレイヤについて、名前とリンクから、手書きと同じ形のプロファイル (下書き) を作り、同じ流れで配置する。

1. **名前の形:** 名前を区切り (`-` `_`) と英字/数字の境でトークンに分け、最も多い形を採用する。形に合わない名前は「分類できない」例外にする。
2. **拠点・役割・番号:** トークンの位置ごとに、「リンクの両端が同じ値になる割合」を求める。高いものが**拠点**、残りで最も低いものが**役割**、末尾の数字が**番号**。
3. **階層:** 拠点をまたぐリンクを持つノードを錨 (上流) にして、錨からのホップ数 (役割ごとの中央値) が小さい順に階層とする。
4. **冗長ペア:** 同じ拠点・役割で番号違いのノードのうち、互いにリンクがある、または隣接ノードが半分以上重なるもの。主は番号が最小のほう。
5. 結果は、手書きと同じ `DiagramProfile` として組み立て、YAML で書き出せる (画面の「Download draft / Copy draft」)。人が直して、正本にする。

拠点が決まらないとき (星形、拠点が 1 つ) や、役割の数が多すぎるとき (12 超、またはノード数の半分超) は、推論しない。役割は名前から取るので、同じ役割名が複数の階層にまたがるデータは区別できない。

## 5. レイヤ間の継承 (`inherit.ts`、`domain/schematicBases.ts`)

上位レイヤ (layer2、layer3 など) は、node の support を下にたどって届く**下位レイヤ**の配置を引き継ぎ、物理図と論理図で拠点の左右・階層・並びをそろえる (P7)。

- **基準レイヤ:** 届く下位レイヤのうち、rank の小さい順に、配置の注釈が作れた最初のレイヤ。プロファイルの `inherit: { from: <レイヤ ID> }` で指定もできる。
- **機器 (下位の 1 つの node に支えられる node):** 配置の主体。その node の拠点・階層・ペアと位置 (x) を引き継ぐ。
- **接続点 (下位の 2 つ以上の node に支えられる node、または継承元の接続点だけに支えられる node。下位レイヤの候補が無くプロファイルで配置するときは、階層を持たず、階層を持つ 2 つ以上の node とつながる node):** L3 のセグメントのような、機器どうしをつなぐ node。`kind` は見ない。**配置の主体ではない**ので、プロファイルにも推論にも例外の報告にも出さない。機器の配置が決まった後に、つながる機器の重心に置く。他のノードや他のリンクに重なるときは、リンクに垂直な方向 (3 つ以上つなぐときは縦) に最小限ずらす (同じ行の離れた機器を結ぶときは上側)。つなぐリンクが他のノードを貫くことは、少しなら許す (1 回あたり 8 ステップ分の移動と同じ費用。ノードやリンクの上に置くことは、どの費用よりも先に避ける)。リンクの迂回は、描画時の経路探索が行うので、貫かない位置まで遠くにずらすと、図が縦に伸びるだけになる (mddo-fw の拠点間の WAN セグメントで、図の高さが半分以下になった)。短いスパンから先に置くので、長いリンクが外側に入れ子になる (`connectors.ts`)。
- 下位レイヤのデータは `ForceView` が読み込み、読み込みが済むまで配置を待つ。

## 6. リンクの経路 (`render/linkRouter.ts`、`render/path.ts`)

schematic では、**ノードやポート (展開した term-point) の円に重なる直線のリンクだけ**を、水平・垂直の線分だけの折れ線 (角を丸める) で描く。

- **描画のたびに現在の位置から**求める。ノードやポートを動かすと、経路全体が追従する (位置が変わっていなければ再計算しない)。
- **形の候補:** L 字 (1 回曲がる)、外側のレーンを通るコの字、中間を通る Z 字。長さと曲がりの数の費用が小さい順に調べ、**障害物 (端のノードとポート以外のすべてのノードとポートの円) に当たらず、他の経路のレーンと離れている**最初のものを使う。無ければ、当たる円が最も少ないもの。
- 短いリンクから先に決める (長いリンクが外側の入れ子)。上側・左側を優先する。同じノードから同じ側に出るリンクは、脚を互いにずらす。
- **ノードとポートに当たらないことを、リンクどうしの交差を避けることより優先する。**
- **ポート:** ポートから出るリンクは、まず円の半径方向に最も近い軸 (上下左右) に短く (8px) 出てから曲がる。経路が必要なリンクのポートは、経路が出ていく向きに置く (まずノードの中心どうしで経路を作り、その最初の線の向きをポートの向きにして、最終の経路を作る)。**ただし、直線のリンクのポートを先に置いて動かさず、経路が必要なリンクのポートは、その空き位置のうち希望の向きに最も近いところに置く。** 直線で済むリンクのポートは、相手ノードの方向のまま。ユーザーが動かしたポートの角度は優先する (優先順位は [layout.md](layout.md) の 3.1)。
- **直線を優先する:** ポートの向きの調整のせいで、直線で済むはずのリンクが折れ線になるときは、その端のノードのポートの向きの調整をやめる。自分のノードの円に食い込むだけの直線 (3px まで) は直線のままにする (円はリンクの上に描かれ、見えないため)。同じノードの別のポートの円に重なる直線は、接続点が分かりにくくなるので迂回する。
- **負荷:** 円を格子で索引して近い円だけを調べる。時間がかかる (6ms 超) ときは、毎フレームではなく、古い経路を描きつつ少し遅れて作り直す。配置の完了直後は間引かない。

## 6.5 手で動かす (`move.ts`、`forceRenderer.ts` の `manualMove`)

schematic では、ノードのドラッグで force のシミュレーションを使わない (他のノードが動いて、行・列の整列が崩れるため)。動かしたノードと、それに連動するノードだけが動く。

- **グリッド:** 動かす量 (ドラッグ開始からの移動量) を 20px に丸める。位置ではなく移動量を丸めるので、行や列の整列は保たれる (`snapDelta`)。
- **範囲:** ドラッグだけ = そのノード。Shift + ドラッグ = 同じレイヤの同じ行 (y が同じ) の機器。Ctrl (Meta) + ドラッグ = 同じ列 (x が同じ) の機器。接続点を動かすときは、その接続点だけ。
- **レイヤ間の連動:** 配置を継承している機器 (`SchematicStructure.follows`: 機器 → 継承元のノード) は、継承元のノードと一緒に動く。逆に、機器が継承元のノードを動かすのは、その機器が継承元のノードを継承する唯一のノードのとき (レイヤ間で同じノード) だけ。1 つの機器から継承する複数のノード (機器のインタフェースなど) のうち 1 つを動かしても、継承元は動かない。
- **接続点:** 機器を動かすたびに、そのレイヤの接続点を機器の間に置き直す (`placeConnectors`。配置のときと同じ処理)。手で動かした接続点は、そのまま残す (配置のやり直しで解除)。
- **操作の案内と強調:** 図の下の情報エリアに操作 (Shift = 行、Ctrl/⌘ = 列) を表示する。修飾キーを押してノードにホバーしている間と、ドラッグ中は、動くノードを強調する (`will-move`: 同じレイヤの行・列のノード、`will-follow`: 連動する他のレイヤのノード)。
- **保存しない:** 手で動かした位置は、再読み込みや snapshot の切り替えで消える。配置のやり直し (`relayout`) でも消える。

`structure` は、レイヤごとの配置の結果 (接続点、リンク、継承元との対応) を `layoutSchematic` が `SchematicLayerInput.structure` で返す。stress レイアウトに落ちたレイヤには無い (行・列の移動だけができる)。

## 7. 例外の報告と画面

- 階層が付かないノード (名前が形に合わない、など)、ペアの規則があるのに相手のいないノードを、レイヤごとに報告する。
- 画面 (図の下の情報エリアのパネル) に、配置の由来 (プロファイル / 継承 (どのレイヤから) / 推論 / なし)、例外の一覧、推論した下書きのダウンロードを表示する。

## 8. 結果 (mddo-fw)

- layer1: 拠点 a → b → c が左から、br → fw → cr → seg → host が上から、ペアは 1 が左で横並び。交差は 3 (stress は 7)。拠点間リンク 6 本が折れ線で、ノードの上を通るリンクは 0 (交差は 9)。
- layer3: 機器は layer1 と同じ拠点・階層・並び、セグメントは機器の間に収まる。交差は 12 (stress は 7)、幅は 560 (stress は 1017)。

## 9. 見送ったもの・限界・今後

- **見送った: セグメントを横線 (バス) として描く** (P10)。試作したが、交差数が改善せず (バスの線を含めて 15、点のままは 12)、見た目の改善も十分ではなかったため見送った。同じ 2 台の機器から出る 2 つの LAN のバスが縦に重なる構造は、横線にしても避けられない。試作は、ブランチ `v0.2.0-dev-schematic-bus` に残してある。再開の目安は、3 台以上をつなぐ LAN が多いネットワークで、点のセグメントが読みにくいと分かったとき。
- **未対応:** 経路どうしの重なりの調整 (並行リンクの脚、L 字の脚どうし)。同型の拠点で配置を共有すること (P6。ステージ 2b)。折り畳みと、手動調整の制約としての保存 (ステージ 5)。基準レイヤを、継承で配置すること。
- **小さいノードのポート:** ポートの順序は希望の向きで決まる (入れ替えての最適化は未対応)。多くのポートが同じ向きに集まると、直線が隣のポートに重なって、迂回になることがある。
- **継承の誤分類のリスク:** 冗長ペア 2 台に支えられる 1 つの論理機器 (クラスタ、VRRP の仮想ルータなど) は、「複数の下位 node に支えられる node」として、接続点と同じに扱われることがある。
- **プロファイルの配信:** 正本は playground の `profiles/<network>/<名前>.yaml`。netomox-exp が JSON にして返す (`GET /topologies/:network/netoviz2/profiles`)。選択は `target` (network / snapshot (正規表現) / layer) による自動選択か `?profile=`。
- **接続点の誤分類のリスク (プロファイルで配置するとき):** 下位レイヤの候補が無いレイヤを、プロファイルで配置するときは、階層を持たず、階層を持つ 2 つ以上のノードとつながるノードを接続点にする。名前の誤記や rule の付け忘れで階層を持たない機器も、2 つ以上の機器とつながっていれば接続点になり、例外として報告されない。継承できるとき、推論のときは、この判定を使わない (報告する)。
- **プロファイルで配置したレイヤを継承元にするとき:** 継承元にプロファイルがあれば、その配置でも上の判定 (階層を持たず、階層を持つ 2 つ以上のノードとつながるノード) で接続点を決める。継承先で、継承元の接続点だけに支えられる node (例: `emulated_asis` の ospf_area の L3 セグメント。layer3 の 1 つのセグメントにだけ支えられる) は、複数の下位 node に支えられなくても接続点になる。これが無いと、セグメントが「階層を持たない機器」と数えられ、半数を超えて継承が拒否され、プロファイルなし (stress) になる。継承元にプロファイルがないとき (推論した配置) は、この判定を使わない。

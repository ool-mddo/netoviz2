## 2. 既存コードの調査結果 (計画に効くもの)

- `LayoutEngine` は `'force' | 'stress'` (`src/render/layout/types.ts:6`)。`LAYOUT_ENGINES` を `ForceView.vue` の `<select>` が描画し、`parseLayoutEngine` が URL を検証する。型に追加すれば UI と URL 検証は自動で追従する。
- `ForceRenderer.layerLayoutOf` (`src/render/forceRenderer.ts:401-403`) は `engine === 'stress'` のときだけレイヤ配置関数を返し、他は force シミュレーションに流れる。**エンジン追加時はここの変更が必須** (放置すると schematic が黙って force で動く)。
- `LayerLayoutFn` の入力は「1 レイヤ内の `{id, radius}` と `{source, target}`」のみ (`types.ts:41`)。名前・tier・TP・support は渡らない。レイヤ順位や層間リンクも渡らない (`forceRenderer.ts:428-431`)。
- `layoutByEngine` (`forceRenderer.ts:414-468`) がレイヤごとに配置関数を呼び、`packBoxes` でグリッドに並べる。
- `engine === 'force'` の二択に依存する箇所: `holdLayout` (703-730)、`reportLayout` (219)、672、704。schematic では force でない側の挙動 (stress と同じ「アンカーに引き戻す」) になるため、意図どおりかを確認する。
- `NodeData` は `id, name, kind?, tp_count`、`TpData` は `id, node, name`、`LinkData` は `src/dst` (`src/api/types.ts`)。ノード名は取得できる。ID は不透明な文字列として扱う方針なので、**名前の分解はプロファイルの正規表現で `name` に対して行い、ID は分解しない**。
- YAML 読み込みは未使用。依存に `yaml` は無い。テストは `src/**/*.test.ts` (vitest + happy-dom)、モジュールと同じ階層に置く流儀。
- 未確認: `domain/layoutScore.ts`、`domain/ports.ts`、`stores/view.ts` の中身、[design/layout.md](../../design/layout.md)。ステップ 0-1 の前に読む。

### 判断 B: プロファイルの供給方法 (決定: 試行段階は B1、最終形は B2)

netoviz2 はローカルファイルを読まず、バックエンドは netomox-exp のみ。

- B1 (試行段階): リポジトリ同梱 (Vite の `?raw` で取り込む) + URL の `?profile=<名前>`。API 追加なし。
- B2 (最終形): netomox-exp が読み取り API でプロファイルを返す。ステージ 1 の範囲外。書き込み API は B2 の後続。
- B1 の読み込み部は「名前を渡すと YAML 文字列が返る関数」に抽象化し、B2 では取得元の差し替えだけで済むようにする。

URL パラメータ `profile` の追加が要る。`CLAUDE.md` の URL 一覧にも反映する。YAML のパース用に `yaml` (ISC) を追加する想定 (導入時にライセンスを再確認)。プロファイルが無い場合は stress と同等のフォールバックにする。

#### プロファイルの配置先 (決定)

トポロジデータはユースケースから独立しているため、プロファイルもユースケース配下には置かない。

- 正本: `playground/profiles/<network>/<snapshot>/profile.yaml` (git 管理。人が書く。`topologies/` は自動生成なので使わない)。
- 試行段階ではこの形で始め、後で調整する (snapshot 単位かネットワーク単位か、など)。
- 1 ファイルに複数ビュー (physical / logical) を入れ、`view` 名で選ぶ。
- B2 では `profiles/` を netomox-exp に mount し、`/topologies/:nw/:ss/profile` のような API で返す想定 (詳細は別計画)。

### 判断 C: プロファイルの YAML 形式

DESIGN.md の例を出発点にする。ステージ 1 で対応する最小のサブセット:
`view`, `target` (network / layer。マッチするレイヤ ID に適用), `tiers`, `name` (正規表現と名前付きグループ), `rules` (`select`, `tier`, `group`, `order`, `pair`)。セレクタは `*`, `[key=value]`, `#id`, `[kind=...]` だけ。後勝ちのカスケードは「後に書いた規則が優先」のみで、詳細度の計算は後回し。`axes`, `inherit`, `shape` はステージ 3 まで読み飛ばす (未知キーは警告のみ)。

### 判断 D3: 例外の報告の出し方 (UI の変更あり)

現在の `SchematicLayerFn` は `Positions` だけを返す。次の変更を提案する。

- `SchematicLayerInput` に任意のコールバック `report(report)` を足す(戻り値の型は変えない)。`ForceRenderer` が受けて、オプション `onSchematicReport` で `ForceView` に渡す。

## 4. 推論のアルゴリズム (D1-a の場合)

1. **形の推定**(`nameShape.ts`): ノード名を区切りと数字でトークンに分け、最も多い形(トークン数と数字の位置)を採用。形に合わない名前は例外 `unclassified` とする。
2. **役割位置・拠点位置の決定**(`infer.ts`): 形の各トークン位置について、値の種類数と、リンクの両端が同じ値になる割合(同類性)を求める。
   - 種類数が 1(定数)または全ノード数(一意)の位置は対象外。
   - 同類性が高く種類数が 2 以上の位置 = **拠点**。同類性が低い位置 = **役割**。末尾の数字 = **番号**。
   - 拠点が決まらなければ(星形、拠点が 1 つなど)推論しない (stress にフォールバックする)。拠点なしで役割だけを決めて錨を別の基準 (次数など) で選ぶ案は、基準レイヤの選択と合わせてステージ 3 で扱う。
   - 役割の数が多すぎる(12 を超える、またはノード数の半分を超える)場合は、役割ではなくほぼ一意な名前とみなして推論しない。
3. **tier**: 拠点をまたぐリンクを持つノードを錨にし、錨からのホップ数を役割ごとに集計(中央値)。小さい順を tier の並びにする。同じ値の役割は名前順で別の tier にする。錨が無ければ tier は推論しない。
4. **ペア**: 同じ拠点・同じ役割で番号だけ違うノードのうち、互いにリンクがある、または隣接ノードの集合が半分以上重なるもの。役割の多数がペアなら、その役割に `pair` 規則を出す。主は番号が最小の値。
5. **下書き**: 推論結果を `DiagramProfile` にする。`tiers` は役割名、`name` は形から組み立てた正規表現(名前付きグループ `site` `role` `index`)、`rules` は役割ごとの `tier`、`group: site`、`pair`。拠点の `order` は書かない(名前順になる)。
6. **例外**: `unclassified`(形に合わない、tier が付かない)、`unpaired`(同じ役割の多数がペアなのに相手がいない)。

決定的であること(同じ入力なら同じ結果)をテストで固定する。

## 2. 調べて分かったこと (mddo-fw、実データ)

4. 完了の目安: 機器の拠点・階層・並びが基準レイヤと一致し、セグメントが機器の間に収まる。交差数は新しい配置で再計測して報告する。バス (3b) は、この配置の見た目を見てから判断する。

# ステージ 4a の改訂: 経路を描画時にその場で求める (実装済み。画面確認とレビューが残り)

状態: **G1〜G4 は承認済み。4a-R1〜R3 を実装済み (未コミット)。4a-1 までは `00cbf5f` にコミット済み。結果: mddo-fw layer1 の経路 6 本、余白 14px 以上、数 ms。ドラッグ・ポートへの追従は ForceRenderer のテストで確認 (d3-drag のイベントは再現できないので、ノード位置を直接変えて draw)。**

## 1. 画面確認での指摘

1. 折れ線の折れる位置が固定で、ノードや term-point (TP) の位置が変わっても追従しない。ノードをドラッグすると見にくくなる。→ **ノードや TP の位置が変わったら、折れ線全体が追従してほしい。**
2. TP の位置によっては、折れ線のリンクが他の TP の下に入って、接続点が分かりにくい。→ **折れ線が、他のノードや TP とかぶらないようにしてほしい。**

## 2. 原因

- 経路を配置の時点で一度だけ作り、固定した点列で描いている (4a-1)。位置が動いても、点列は動かない。
- 経路の計算は、ノードの円だけを障害物にしている。TP (ノードの円周上の小さなポート) は障害物にも、リンクの端の向きにも考慮していない。
- 「同じ行」の仮定 (`rowOf` の一致) で経路を作っているので、ノードが行から外れると、そもそも作れない。

## 3. 改訂案

### 判断 G1: 経路は描画のたびに、現在の位置から求める (承認済みの F3 を置き換える)

- 配置 (`layoutSchematic`) の `routes` コールバックと、レイアウト時の経路は廃止する。経路は、`ForceRenderer` が、現在のノードとポートの位置から、描画のたび (ドラッグ中は毎ティック) に求める。
- schematic エンジンのときだけ行う。stress / force は直線のまま。
- 計算量は、「直線がノードやポートに当たるリンク」だけが対象。ノードとポートが数百〜千のとき、1 回に数 ms の見込み。位置が変わっていなければ、前の結果を再利用する。

### 判断 G2: 障害物と端点

| 項目         | 内容                                                                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 障害物       | すべてのノードの円と、すべてのポート (TP) の円。リンク自身の端のノードとポートは除く                                                     |
| 端点         | 折り畳んだリンク: ノードの中心。展開したリンク: ポート                                                                                   |
| 端の向き     | ポートから出るリンクは、まずノードの外向き (円の半径方向) に短く出てから (数 px)、迂回する。ノードの円の内側や、他のポートの下を通らない |
| 自分のノード | 端のノード自身の円と、その他のポートは、出口の短い線より先の区間で障害物とする                                                           |

### 判断 G3: 経路の求め方 (4a-1 のレーンを、任意の向きに一般化する)

- 2 つの端点を結ぶ直線が、障害物に当たるときだけ、迂回する。当たらなければ直線のまま。
- 迂回は、端点を結ぶ線に**垂直な方向**に「脚 → 平行な区間 → 脚」の台形の折れ線 (4a-1 と同じ形で、向きが任意)。垂直な向きは、上側 (y が小さい側) を優先する。
- 平行な区間 (レーン) は、端点から近い順に試し、**障害物 (ノードとポート) に当たらず、他の経路の区間と離れている**最初のものを採る。他の経路の区間との距離は、線分どうしの距離で判定する (どの向きでも同じ判定)。
- 短いリンクから先に割り当てる (内側のレーン。入れ子)。順序は決定的 (長さ、ID の順) にして、ドラッグ中にちらつかないようにする。
- ご指示の優先順位に従い、**ノードとポートに当たらないことを最優先**し、リンクどうしの交差は許容する。ただし、レーンが重ならないようにはする。
- 行に並んだノードでは、4a-1 と同じ見た目になる (行の上下のレーン)。

### 判断 G4: ポートの置き方

- 今のポートは、相手ノードの方向に置く。経路があるリンクのポートは、**最初の中継点の方向**に置く方が自然だが、「経路がポートの位置に依存し、ポートが経路に依存する」循環になる。最初は、今のまま (相手の方向) にして、出口の短い線 (G2) で吸収する。見た目が悪ければ、後続で 2 段階 (ノードだけで経路 → ポートの向き → 最終の経路) にする。

## ステージ 4a の改訂 2 (画面確認を受けた修正)

画面確認での指摘: (1) 折れ線を水平・垂直にしてほしい (斜めに傾いた折れ線は、かえって見にくい)、(2) 折れ線にする必要がないところは直線のままにしてほしい (折れ線にするのは、直線で引くとノードとリンクが被るものだけ)。

- (1) 経路を水平・垂直の線分だけに変更した。端点を結ぶ線に垂直なレーンをやめ、L 字・外側のレーン (コの字)・中間 (Z 字) の候補から、費用 (長さ + 曲がり) が最小で障害物に当たらないものを選ぶ。ポートの出口の短い線も、半径方向に最も近い軸 (上下左右) に合わせる。

(High-1) 円の空間索引 (格子) と、時間がかかるときの間引き (古い経路を描きつつ遅れて作り直す)。(Medium-1, 3) ポートの端のノード自身の円は、余白ではなく「円の中に入らない」だけを条件にした (大きなノードで 45° 付近のポートの出口が余白に入り、障害物ゼロの候補が無くなる問題、およびポートが相手と反対側にあるとき自ノードを貫く直線が迂回されない問題)。(Medium-2) リンクの構成が変わったとき (同じノードのままリンク ID だけが変わる場合) に経路を作り直す。(Low) 脚をずらす軸を経路の種類から決める、1 本だけの脚はずらさない、JSDoc、到達しない分岐の削除。レビュー後の自分の確認で、空間索引の導入時に作り込んだ不具合 (区間をまたいで「見た円」を共有し、後の区間で調べ漏れる) を見つけて修正し、回帰テストを追加した。

未対応 (記録): (Low-2) L 字の脚どうし、ポート端の脚どうしの重なりは検出しない (同じ x を通る縦の脚が 1 本に見える可能性)。(Low-6) 経路が動的になったため、レイヤの外接矩形 (packBoxes) に経路は含まれない (外側のレーンが隣のレイヤに入りうる。障害物には全レイヤのノードが入っているので、隣のレイヤのノードは避ける)。ポートをドラッグしたときの経路の追従は、テスト未整備。

### G4 の実装 (ポートの向きを経路に合わせる)

ポートと経路の循環 (経路はポートの位置に依存し、ポートの向きは経路に依存する) を 2 段階で解いた: (1) ノードの中心どうしで経路を作り (直線で済むリンクは対象外)、その最初 (最後) の線の向き (上下左右) を、そのリンクのポートの希望角度にする。(2) 希望角度でポートを置き (同じ向きのポートは `spreadAngles` で離す)、ポートを端点とする最終の経路を作る。ユーザーが動かしたポートの角度 (`pinnedAngles`) は、そのまま優先する。経路が不要になった (邪魔なノードを動かした) ときは、相手ノードの方向に戻る。

### G4 の画面確認を受けた修正 (直線にできるところは直線)

指摘: fw-1/2 の間のリンクが、直線にできるはずなのに、ポート位置の調整で折れ線になっていた。調査: (a) 初回の描画で、計算時間による間引きが働き、配置の完了前の位置から求めた古いポートの向きと経路が、数百 ms 残っていた (実データで折れ線 34 本 → 収束後 8 本)。(b) 収束後も、ポートの向きの調整で押し出されたポートが、同じノードの別のポートの近くを通り、直線が折れ線になるものが数本あった。対応: (a) 新しいグラフの描画と配置の完了直後は、間引かずに経路を作る (9 本に減り、その後 8 本に収束)。(b) ノード中心どうしでは直線で済むリンクが折れ線になった場合は、その端のノードのポートの向きの調整をやめる。自分のノードの円に食い込むだけの直線 (3px まで) は直線のままにする。残る br と fw の間の 2〜3 本は、小さいノードの 5 個のポートが 72° ずつ均等に並び、直線が隣のポートに 2px 重なるもので、迂回を残した (ポートの順序や回転を最適化すれば直線にできる可能性があるが、未対応)。
